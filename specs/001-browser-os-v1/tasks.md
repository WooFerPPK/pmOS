# Tasks: Browser OS v1 — Initial Release

**Input**: Design documents from `/opt/webos/specs/001-browser-os-v1/`
**Prerequisites**: `plan.md`, `spec.md`, `research.md`, `data-model.md`, `contracts/` (syscalls, display-protocol, driver-kernel, package-manifest, init-conf), `quickstart.md`, `.specify/memory/constitution.md`

**Tests**: Principle X of the project constitution **mandates** isolation tests at every layer before integration. Test tasks are therefore **not optional** in this feature — they are constitutional requirements. Integration tests (Playwright) are also mandatory per Principle X's "integration tests cover the full stack" clause.

**Organization**: Tasks are grouped by phase. Phase 1 is Setup, Phase 2 is Foundational (all of kernel + drivers + display server + toolkit + init — bottom-up per Principle VIII). Phases 3–12 are one-per-user-story in priority order, each delivering a user-visible increment on top of the foundation. Phase 13 is Polish.

## Format: `[ID] [P?] [Story?] Description`

- **[P]**: Can run in parallel (different files, no dependencies on incomplete tasks in the same phase)
- **[Story]**: Which user story this task belongs to (US1–US10); Setup / Foundational / Polish tasks have no story label
- Every task includes exact file path(s) in its description

## Path Conventions

Paths are repository-relative (repo root is `/opt/webos/`). The Rust workspace lives at the root (`Cargo.toml` + `crates/`). The TypeScript tree lives under `web/`. The final static deploy directory is `dist/` (gitignored). Spec/plan/contracts live under `specs/001-browser-os-v1/`.

- [x] T071 WASI preview 1 handler in `crates/kernel/src/syscall/wasi.rs` implementing every opcode from `contracts/syscalls.md §2` (args, environ, clock, fd, path, poll, proc, random, sock, sched) — **closed (final opcode `FD_FDSTAT_SET_RIGHTS` stub landed in fe198de; FD_READDIR wire+adapter pre-existing + Kernel::fd_readdir semantic seam in 08cab5b; FD_WRITE / FD_READ / FD_CLOSE / PATH_OPEN / PROC_EXIT in T073 first-landing)**: `crates/kernel/src/syscall/wasi.rs` ships `dispatch_wasi` with a match arm for every named WASI preview 1 opcode in `abi::wasi::op`. `FD_FDSTAT_SET_RIGHTS` returns `ENOTSUP` rather than falling through to `ENOSYS` — PMos uses its own capability system (`cap_*` extension syscalls 0x1300..0x1302) instead of WASI's per-fd rights vectors, so rights narrowing is genuinely unsupported (returning `ESUCCESS` would lie — userland would assume rights were narrowed when they weren't; `ENOTSUP` takes precedence over `EBADF` since the operation itself is unsupported regardless of fd validity). Wire format: `target_pid` as u32 in `args[0..4]`, `caps_to_grant` as u64 in `args[4..12]`, no heap. Semantic: caller MUST hold `Cap::CapGrant` (else `-ENOTCAPABLE`); target pid must exist in process table (else `-ESRCH`); `caps_to_grant` MUST be a subset of the caller's own caps — no widening (any bit set in `caps_to_grant` but missing from caller → `-ENOTCAPABLE`, atomic reject, target untouched). On success, target's caps become `target.caps ∪ caps_to_grant` (union — never strips caps). The semantic primitive lives in `crates/kernel/src/cap/mod.rs::CapTable::grant(granter, target, caps)` which already existed pre-slice with the exact spec semantics — `is_superset_of` for the subset check, `union` for the merge, `CapError::{NotPermitted, NotASubset}` both collapse via `From<CapError> for KernelError` to `KernelError::NotCapable` so the standard `kerr_to_errno` mapping yields `-ENOTCAPABLE` for both arms (probe-resistance against permission-set inference). Wire format per `contracts/syscalls.md §3.1`: `fd` as u32 in `args[0..4]`, `len` as u32 in `args[4..8]`, `fd_to_pass` as i32 in `args[8..12]` (-1 = none, any non-negative = an fd-number that must exist in the caller's table), `flags` as u32 in `args[12..16]` (v1 only accepts 0 — any other value → `-EINVAL` before any side effect), and the payload bytes at `heap[heap_ptr .. heap_ptr+len]` with the `len` arg cross-checked against `req.heap_len` (mismatch → `-EINVAL`). Semantic routing by fd object: `FdObject::Socket` calls the existing `IpcTable::send_on_socket(sender_id, buf, passed_fds: Vec<u32>)` primitive (which already queues passed fd numbers on the peer's `Socket::rx_fds` queue — the receiver-side translation into a fresh `FdEntry` is the IPC_RECV slice's job, not this one); `FdObject::PipeWrite` calls `Pipe::try_write` on the existing pipe primitive but rejects `fd_to_pass.is_some()` with `-EINVAL` since pipes are byte streams without an ancillary channel; any other fd object → `KernelError::NotSupportedOnFd` which the handler folds to `-EBADF` rather than the generic `-EINVAL` (the spec calls "wrong fd kind" on an IPC opcode `EBADF`, distinct from FD_WRITE's EINVAL — matching POSIX `send(2)` / `sendmsg(2)`'s documented contract). `fd_to_pass` validity is checked BEFORE the bytes are queued: a bad ancillary fd produces `-EBADF` with the receiver's rx_buf and rx_fds both untouched (atomic-reject — no partial send where the payload lands without the ancillary fd, which would deadlock a recv that asked for both). Pipe-broken outcomes additionally post `Signal::Pipe` to the caller's signal inbox via `Kernel::post_sigpipe`, mirroring `fd_write`'s POSIX-shaped EPIPE / SIGPIPE pairing. Wire format per `contracts/syscalls.md §3.1`: `fd` as u32 in `args[0..4]` (the connected socket to drain), `len` as u32 in `args[4..8]` (max payload bytes the caller will accept this call), `recv_fd_slot` as i32 in `args[8..12]` (`-1` = "don't install a passed fd; leave any queued fds on the socket's rx_fds for a later call"; any non-negative = "install one queued fd in the lowest-free slot of my fd table" — v1 ignores the actual slot value beyond the sign, slot-targeted install is a future extension), and `flags` as u32 in `args[12..16]` (v1 only accepts 0 — any other value → `-EINVAL` BEFORE any side effect, mirroring ipc_send's atomic-reject invariant). Heap layout: the OUTPUT region at `heap[heap_ptr .. heap_ptr+heap_len]` carries the drained payload bytes plus, when an fd was installed, a leading 4-byte little-endian u32 holding the new receiver-side fd-number (payload follows from offset 4). When `recv_fd_slot >= 0`, `heap_len` MUST be at least `len + 4` (else `-EINVAL` before the recv side-effect commits); when `recv_fd_slot < 0`, `heap_len` just needs to cover the requested `len` bytes. Response: `value` = number of payload bytes drained (>= 0, independent of whether an fd was installed); `extra_len` = total bytes the kernel wrote into heap_out (`bytes` if no fd was installed, `4 + bytes` if one was). The fd-leading heap layout matches the existing dispatcher convention — `proc_wait` writes its reaped child pid at `heap[0..4]`, `ipc_pipe` writes its dual fds at `heap[0..8]`; every multi-value Response in the dispatcher uses fixed offsets, never variable ones. The alternative (payload first, fd at `heap[value..value+4]`) would force the caller into a two-pass parse — first read `value` from the Response, then walk to the offset — which breaks the natural POSIX-shaped `recv(fd, buf, len)` read pattern. Bit-packing the fd into `Response.value` alongside the byte count was rejected: `value` carries the conventional "primary scalar return" (matching FD_READ / IPC_SEND's "value == bytes") and squeezing two scalars into one i64 would break that pattern; the heap-extra path costs 4 bytes per recv — negligible. If any step of the translation fails (sender process exited between send and recv, sender closed the fd before recv, peer pointer became `None`), the queued u32 is silently dropped and the receiver gets `Ok((bytes, None))` — a deliberate v1 degradation; a more rigorous implementation would resolve the underlying object at SEND time and queue the `FdObject` directly (eliminating the dangling-fd race), but the IPC_SEND slice committed to queueing only the u32 number and changing that is a separate IPC-table refactor. **`recv_fd_slot = -1` semantics**: the rx_fds queue is left untouched even if it has entries waiting; a subsequent `ipc_recv` with `recv_fd_slot >= 0` can drain them. ### Phase 2 Known Deviations

These are cross-cutting deviations that exist in the repository as of commit `cb41cfb` and do not fit cleanly into any single T-ID note. They are recorded here (per the constitution's "Deviation log" requirement) so that a future reader looking for the originally-planned structure understands where the code actually lives and why.

1. **`crates/display-proto/` crate extraction** — a shared protocol codec crate was extracted out of `display-server/` so that `display-server`, `toolkit`, and `toolkit-free-client` can all depend on the same wire encoding, object-ID rules, request/event enums, and interface definitions. 2. **`crates/kernel/src/sys.rs` + the `Kernel` struct** — rather than implementing the syscall dispatcher first (T071/T073) and hanging semantic logic off it, the kernel exposes a semantic Rust method surface on `Kernel` that native tests (`crates/kernel/tests/sys.rs`) drive directly. `Kernel::proc_spawn`, `proc_wait`, `proc_kill`, `path_open`, `fd_read`, `fd_write`, `fd_close`, `display_bind`, `display_connect`, `drain_signals`, etc. all live there. When T071/T073 land, the opcode dispatcher will sit on top of this surface and translate SAB ring requests into method calls — **it will not replace `sys.rs`**. The module-level doc comment in `sys.rs` records this explicitly ("T071..T078" wraps this struct).

3. **`crates/toolkit/src/protocol.rs` + `theme.rs`** — the toolkit has its own wire-protocol client (`protocol.rs`, 622 lines) that speaks directly to `display-proto`, independent of T114's `App::connect`. T114 is now framed as a thin facade extraction over `protocol.rs`, not a reimplementation — `App::connect` will create a `Client` from `protocol.rs` and expose an event loop around it. Tests at `crates/toolkit/tests/{protocol,loopback}.rs` already exercise the full client through a mock display server. `theme.rs` ships ahead of its nominal home (T184, the settings app) because `WindowFrame` (next slice) needs theme colours to paint chrome — the theme struct + default light/dark palettes live here now. **Settings-app integration remains T184**; `theme.rs` today is just the data model + defaults.

4. **`crates/term/` + the TypeScript preview slice** — `crates/term/` and the TS files `web/src/{terminal,mock-kernel,console-host,console-check,fb-host}.ts` + `web/src/shared/{rasterizer,font,worker-proto,input-proto}.ts` are a visible-progress demo slice built before real kernel IPC (T072) and the real `/run/display` accept loop (T110) exist. Treat this block as scaffolding that will be partially deleted, not as completed user-facing work.

**Independent Test**: Playwright runs the exact pipeline in a terminal, asserts `out.txt` content is exactly the filtered lines, asserts no zombies remain.

The `numeric && fold && unique` combination uses plain `dedup()` since numeric dominance means the fold key isn't computed for sort and the dedup boundary should match the sort key (numeric here). +7 integration tests in `crates/coreutils/tests/sort.rs` (sort tests 14 → 21): `dash_f_sorts_case_insensitively` (`Banana\napple\nCherry\n` → `apple\nBanana\nCherry\n` — pins that capital-B sorts AFTER lowercase-a under fold, which raw-lex would have given `Banana\nCherry\napple\n` since uppercase bytes are smaller); `dash_f_preserves_original_case_in_output` (`Apple\nbanana\n` → `Apple\nbanana\n` byte-identical — pins the comparison-only-not-content-mutation invariant); `dash_fu_dedupes_case_insensitive_duplicates` (`Apple\napple\nAPPLE\nbanana\n` under `-fu` → `Apple\nbanana\n` — pins that `dedup_by_key` keeps the FIRST entry of each fold class after the stable sort, and that all three case-variants of `apple` collapse to one); `dash_fr_reverses_case_insensitive_sort` (`apple\nBanana\nCherry\n` under `-fr` → `Cherry\nBanana\napple\n` — pins fold + reverse interaction giving descending case-insensitive order); `dash_fn_combines_but_n_dominates` (`-fn` on `2\n10\n` → `2\n10\n` — pins that `-f` is a no-op when `-n` is set, since numeric sort dispatches first in the `if/else if/else` chain and `parse_leading_int` is case-insensitive by definition); `dash_f_handles_non_ascii_bytes_passthrough` (input with the UTF-8 byte sequence 0xC3 0xA9 for `é` plus `Apple\nbanana\n` — sorts as `Apple\nbanana\nÉ\n` since 0xC3 (195) is greater than uppercase B (66), pinning that the slice is byte-level not codepoint-level and no Unicode folding is attempted); `dash_f_alone_with_no_input_is_empty_output` (empty stdin under `-f` → empty stdout, exit 0 — sanity check that the flag doesn't break the empty-input path). ## Dependencies & Execution Order

### Phase Dependencies

- **Phase 1 (Setup)**: no dependencies; can start immediately.
- **Phase 2 (Foundational)**: requires Phase 1. **Blocks all user story phases.** This is the constitution's bottom-up gate and is non-negotiable.
- **Phase 3 (US1 — MVP)**: requires Phase 2.
- **Phases 4 (US2), 5 (US3)**: require Phase 2; independent of each other and of Phase 3 in design, but US2 and US3 add minor integration glue that is easier to validate against a running US1.
- **Phases 6–12 (US4–US10)**: require Phase 2 and benefit from Phases 3–5 being in place (they share the desktop shell, file manager, and terminal).
- **Phase 13 (Polish)**: requires all desired user-story phases to be complete.

### User Story Dependencies

- **US1**: the absolute minimum. Every later story builds on top of its shell + terminal.
- **US2**: extends US1 with window management chrome. Independent in design.
- **US3**: the persistence story; end-to-end tests depend on US1 existing so that `mkfs` can seed a usable home directory. Logically independent.
- **US4**: extends `/usr/bin/sh` from US1's minimal stub to a full shell. Independent in design.
- **US5**: introduces the files and edit apps. Independent but benefits from US4 existing for the terminal-side install workflow shown in `quickstart.md §5`.
- **US6**: offline verification; depends on US1/US2/US3/US5 for the apps it tests launching offline.
- **US7**: sysmon; can be implemented as soon as `/proc` works (US7's real dependency is T054, not on earlier user stories).
- **US8**: the layering test. Depends on US2 (window management), US7 (sysmon for the "kill shell" step), and the `pmd_shell_manager` replay from Phase 2.
- **US9**: the settings app. Independent of US4/US5/US6/US7/US8 in design; touches the toolkit's theme path and the display server's keymap path.
- **US10**: third-party install. Depends on US5 (the file manager's drag-drop import path) and the launcher watcher added in this story.

### Within Each User Story

- Test tasks marked [P] in the same story can run in parallel (they touch different files).
- Implementation tasks that touch the same file must run sequentially.
- Per Principle X, the isolation tests at the crate level must be green before the Playwright integration tests can claim the story is done.

### Parallel Opportunities

- All Phase 1 `[P]` tasks (T005–T025 excluding sequential ones) can run simultaneously; the crate skeletons are independent.
- In Phase 2, once T030–T038 (abi + ring + layout generator) are complete, the kernel, drivers, display server, and toolkit tracks can all proceed concurrently against a frozen ABI. Specifically:
  - Kernel track (T039–T078)
  - TS driver track (T079–T094)
  - Display server track (T098–T113) (once kernel IPC and caps exist)
  - Toolkit track (T114–T120) (once display protocol decoder exists)
  - Init track (T095–T097)
- All Playwright integration tests in a given story can run in parallel against separate browser contexts.

## Implementation Strategy

### MVP First (Phases 1 + 2 + 3)

1. Complete Phase 1 (Setup).
2. Complete Phase 2 (Foundational) — this is the big one. No short-cutting.
3. Complete Phase 3 (US1 — First Boot to a Usable Desktop).
4. **STOP and VALIDATE**: run `just test`. Must pass four isolation test targets and `boot-to-desktop.spec.ts`. Open `just dev` in a fresh browser profile; confirm the desktop boots and `echo hello` in the terminal works.
5. Deploy to Cloudflare Pages and run the deployed Playwright test. The MVP is shippable.

### Incremental Delivery (Phases 4–12)

Run each user-story phase sequentially, validating and deploying after each:

- Phase 4 (US2) → full window management.
- Phase 5 (US3) → end-to-end persistence verified.
- Phase 6 (US4) → real shell pipelines.
- Phase 7 (US5) → files + edit + host ↔ PMos transfer.
- Phase 8 (US6) → offline-first empirically gated.
- Phase 9 (US7) → system monitor.
- Phase 10 (US8) → **layering test passes** (the constitution's acceptance gate).
- Phase 11 (US9) → full settings app.
- Phase 12 (US10) → third-party app install.

After US8 passes, the architectural claim of the project is verified. Everything afterwards is feature breadth.

### Parallel Team Strategy

With multiple developers:

1. Team completes Phases 1 and 2 together (with internal parallelism as above).
2. Once Phase 2 is green:
   - Developer A: Phase 3 (US1 MVP) → Phase 4 (US2 windowing)
   - Developer B: Phase 5 (US3 persistence) → Phase 8 (US6 offline)
   - Developer C: Phase 6 (US4 shell) → Phase 7 (US5 files + edit)
   - Developer D: Phase 9 (US7 sysmon) → Phase 10 (US8 layering test)
3. Re-converge for Phase 11 (US9 settings) and Phase 12 (US10 third-party install).
4. Phase 13 (Polish) together.

## Notes

- Principle VIII (bottom-up construction) is encoded in the phase order and specifically in the T077 headless-shell gate that ends the kernel's sub-phase of Phase 2 — the kernel is required to be demonstrably useful before the display server is started.
- Principle X (testability at every layer) is encoded in the requirement that every crate in Phase 2 lands with a matching isolation test task (T036, T038, T046, T048, T055, T061, T064, T066, T077, T078, T081, T083, T085, T087, T089, T093, T094, T097, T111, T112, T120), that no user-story phase has implementation tasks without matching tests, and that integration tests (Playwright) never substitute for isolation tests.
- Principle II (strict layering) is encoded in the `pmd_shell_manager` replay (T105) + the layering-test integration test (T181). T182 explicitly marks it as a build gate.
- Principle IX (performance budget) is encoded in T128 (US1 cold-load budget check) + T208 (final audit). Every task whose expected budget impact is uncertain should record it in a comment at implementation time.
- Every task above names exact file paths so an LLM or a developer can open the task, create the file, and work without re-reading the plan. Tasks without file paths ought to be split further.
- Test tasks are mandatory per Principle X; a PR that adds implementation without its matching test task being closed cannot be merged.
- Commit after each task or each tightly-related group. The auto-commit hooks (`after_tasks`, `after_implement`) exist for exactly this.
